# Compiled migrations

Миграции принадлежат приложению и компилируются вместе с ним. ORM применяет
`MigrationOperation` и записывает идентификаторы и контрольные суммы в историю
базы. Изменение модели само по себе не обновляет существующую схему.

Физические имена таблиц должны соответствовать `[a-z_][a-z0-9_]*`.
Это правило применяется к моделям, зарегистрированным SQL-таблицам, целям
внешних ключей в метаданных и операциям переименования. Имя в метаданных
пишется без кавычек. Компилятор может заключать допустимое имя в кавычки в SQL.

Предлагаемое устройство следующей версии планировщика и критерии выпуска
описаны в [архитектурном проекте](migration-design.md).

## Генерация в своём приложении

Самый простой путь — [шаблон приложения](template.md). Он включает исходники
CLI `manage` и пустой реестр миграций. Установка зависимости
`che-orm` сама по себе не добавляет CLI в существующий проект.

Зарегистрируйте модели в `AppConfig::schema()`, а модули приложения — в
`AppRegistry`, в порядке зависимостей: родители раньше моделей с внешними
ключами. Затем из каталога сгенерированного приложения создайте первую миграцию:

```bash
cargo run --bin manage -- makemigrations --name initial
```

Генератор сравнивает зарегистрированные модели с состоянием, восстановленным
из предыдущих миграций, а не с живой БД. Он записывает пронумерованный Rust-модуль
и обновляет `mod.rs` в соответствующем каталоге миграций. Для генерации не нужна
БД, но нужен `rustfmt`.

При начальной генерации порядок определяется зависимостями отдельных
операций, включая ссылки на зарегистрированные SQL-таблицы и представления.
При цикле между новыми моделями разных приложений генератор может добавить
внешние ключи отдельной фазой после создания таблиц. Представления и триггеры,
которые требуется временно снять при перестроении таблицы, восстанавливаются
в той же миграции. Каждый зарегистрированный SQL-объект описывается одним
оператором `CREATE`. Тело триггера SQLite может содержать несколько команд.

| Структура шаблона | Где хранятся миграции | Как применяются |
| --- | --- | --- |
| `single` | Общий каталог `src/migrations/`. | CLI читает общий реестр. |
| `modular` | `apps/<app>/src/migrations/` в крейте владельца модели. Нумерация отдельная для каждого крейта. | Корневой `src/migrations.rs` собирает миграции зарегистрированных крейтов в один граф. |

Например, `tasks:0001_initial` и `blog:0001_add_blog` — разные миграции
несмотря на одинаковый номер. Если `blog` ссылается на таблицу `tasks`,
зависимость в графе позволяет применить миграцию `tasks` раньше `blog`.
Одна команда `makemigrations` может записать файлы в несколько крейтов.

Проверьте операции перед применением, особенно удаления, переименования
и новые обязательные поля в непустых таблицах. Перенос данных и явные
переименования могут потребовать ручной правки. Добавьте файлы миграций в Git.

```bash
cargo run --bin manage -- migrate
cargo run --bin manage -- migrate status
```

После следующих изменений моделей создавайте новые миграции:

```bash
cargo run --bin manage -- makemigrations --name update_models
cargo run --bin manage -- migrate
```

Не меняйте уже применённые миграции: их идентификаторы, содержимое и контрольные
суммы должны сохраняться. Применение — отдельный шаг деплоя, не часть старта
приложения. Генерация тоже всегда выполняется явно.

## Политика генерации

Для намеренного удаления укажите физическое имя, например
`makemigrations --name cleanup --drop blog_post.obsolete`. Для нескольких
объектов повторите `--drop`. Изменение SQL-описания существующей таблицы, типа
колонки или добавление обязательного поля без default требует ручной миграции
(`NeedsManualMigration`). Для SQL-таблицы можно выполнить `ALTER TABLE` через
`RunSql` и заменить её описание в `state_operations`: эти операции не исполняют DDL.

`generate_with_policy` принимает `GenerationPolicy`: `sql_tables` задаёт
`SqlTableContract` (предоставляемые ключи и требуемые пары таблица/колонка),
`external_keys` — ключи вне проекта. Таблица из `SchemaObjectKind::Table`
считается управляемой даже без контракта: реестр определяет её владельца,
а БД проверяет физический ключ. Задайте `strict_external: true`, чтобы опечатка
в имени внешнего ключа не проходила офлайн-проверку.

## Просмотр изменений и CI

```bash
cargo run --bin manage -- makemigrations --dry-run
cargo run --bin manage -- makemigrations --check
```

`--dry-run` печатает предложенный Rust-код без записи файлов. `--check`
завершается с ненулевым кодом, если модели требуют новой миграции.
Обе команды работают без подключения к БД. Запускайте через `cargo run`,
чтобы использовать актуальные модели и реестр: устаревший бинарник отклоняет
генерацию при изменении исходников миграций.

Для PostgreSQL заранее создайте базу и задайте `CHE_ORM_DATABASE_URL`.
В шаблоне backend выбран при генерации; при его переключении используйте
`--no-default-features --features postgres` на каждой Cargo-команде.
Структурированные операции компилируются для выбранного backend, но произвольный
SQL и преобразования данных требуют проверки под конкретную БД.

## CLI приложения-примера

Из корня репозитория:

```bash
cargo run -p che-orm-examples --bin manage -- schema
cargo run -p che-orm-examples --bin manage -- migrate
cargo run -p che-orm-examples --bin manage -- migrate status
```

`schema` печатает схему зарегистрированных моделей. `migrate` применяет
миграции, а `migrate status` показывает, какие из них записаны в историю.

`database_url()` в `example/orm-api/src/lib.rs` читает `CHE_ORM_DATABASE_URL`.
По умолчанию SQLite использует `app.db`, PostgreSQL - `postgresql://localhost/che_orm`.
Для PostgreSQL добавьте `--no-default-features --features postgres` перед `--bin`.

Начальная Rust-миграция `examples:0001_initial_models` в
`example/orm-api/src/migrations/` общая для SQLite и PostgreSQL. Если вы уже
применяли старую SQL-миграцию, укажите новую БД через `CHE_ORM_DATABASE_URL`.
Команды `makemigrations` и `migrate lint` в этом примере недоступны.

## Собственный реестр и API

Храните модели, `AppRegistry`, настройки и реестр миграций вне core-крейта.
Создавайте миграции через `Migration::new`, указывая стабильные `MigrationId`,
зависимости и последовательность `MigrationOperation`.

```rust
let graph = che_orm::MigrationGraph::new(application_migrations())?;
let applied = database.migrate(graph).await?;
```

`application_migrations()` - функция вашего приложения, возвращающая
`Vec<Migration>`. Для генерации новых файлов вызовите
`graph.generate(&desired, MigrationLayout::PerApp, "update_models")` (или
используйте `MigrationLayout::Single("tasks")`), затем передайте каждую новую
миграцию в `render_migration_rust`. `desired` — `ProjectState` из реестра приложений.
Оба шаблона используют этот API: один `ProjectState::diff` не задаёт порядок
выполнения. Планировщик проверяет каждый файл с учётом его предшественников и
выбранного backend без подключения к БД. Если порядок подобрать невозможно,
CLI сообщает о заблокированных операциях до записи файлов.
Проверяйте полученные операции и SQL до применения. `RunSql` должен содержать
SQL выбранного backend и соответствующие `state_operations`, если меняет схему.

Не изменяйте идентичности, содержимое и checksums уже применённых миграций.
Добавляйте новые операции в новые миграции; backfill существующих данных
планируйте явно. Например, обязательному `DbEnum` в непустой таблице нужно
заполнить допустимое значение, сохранив его `CHECK` constraint.

Применение миграций - отдельный шаг deploy/CI. `Database::create_table` оставьте
для тестов и локальных экспериментов. Особенности блокировок, транзакций и SQL
обоих backend описаны в [руководстве backend](backends.md#миграции).

## Переименование, ручные миграции и ветки

При переименовании Rust-модели укажите приложение, старое и новое имена. Для
переименования колонки укажите прежнее физическое имя таблицы и колонки. Если
меняется только имя Rust-поля, сохраните имя колонки через `db_column`.

```bash
cargo run --bin manage -- makemigrations --rename-model tasks.Task WorkItem --name rename_task
cargo run --bin manage -- makemigrations --rename-field tasks_task.notes description --name rename_notes
```

Первый пример записывает новое имя модели в историю. Если новое объявление
меняет и SQL-имя таблицы, генератор также планирует её переименование. Второй
переносит существующие значения колонки. Обновите определения представлений
и триггеров, которые ссылаются на прежнюю колонку. Генератор снимает зависимые
объекты перед переименованием и восстанавливает их по реестру в порядке зависимостей.
Для непрозрачного SQL, включая CHECK,
который мешает автоматическому переименованию, подготовьте ручную миграцию.
`--drop` предназначен для намеренного удаления данных.

```bash
cargo run --bin manage -- makemigrations --empty tasks --name backfill_notes
cargo run --bin manage -- makemigrations --merge tasks --dry-run
cargo run --bin manage -- makemigrations --merge tasks
```

`--empty` создаёт и регистрирует файл с зависимостью от текущей конечной
миграции. Заполните его операции до первого применения. Например, для нового
обязательного поля добавьте nullable-колонку, заполните её через
`BackfillColumn`, затем установите ограничение через `AlterColumn`.
В структуре single указывается владелец общего каталога миграций.
В modular служебная история с владельцем `che_sync` находится в
`src/che_sync_migrations/`.

После объединения Git-веток включите оба файла в Rust-реестр и разрешите
конфликты компиляции. `--merge` создаёт миграцию с зависимостями от всех
конечных миграций приложения. Независимые таблицы и добавление разных простых
nullable-колонок могут объединяться автоматически. Пересечение операций с
произвольным SQL или конфликт схемы требует ручного разбора обеих веток.
Это относится и к `BackfillColumn`: его SQL-выражение может читать данные,
изменяемые параллельной веткой.

## Проверка перед применением

```bash
cargo run --bin manage -- migrate status
cargo run --bin manage -- migrate tasks 0002_rename_task --plan
cargo run --bin manage -- sqlmigrate tasks 0002_rename_task
cargo run --bin manage -- migrate tasks 0002_rename_task
```

`status` проверяет контрольные суммы и зависимости; расхождение даёт ненулевой
код выхода. `--plan` читает историю и перечисляет оставшиеся операции в порядке
выполнения. Цель задаётся полным именем файла миграции без префикса модуля
`m` и расширения. Целевое применение включает её зависимости и работает вперёд.
`sqlmigrate` показывает SQL операций для выбранного backend без подключения к
БД. Проверки реальных строк, блокировка и обновление истории выполняются при
`migrate`.

Перед перестройкой SQLite сверяет колонки через `pragma_table_xinfo`. Если в
таблице есть данные в незарегистрированной колонке, исполнитель останавливает
миграцию: перенесите данные и согласуйте схему отдельной проверенной операцией.

После переименования таблицы SQLite может сохранить прежние имена индексов.
Если такое имя потребуется таблице, представлению или индексу, генератор
включит в план освобождение имени. SQLite проверяет принадлежность и определение
индекса и пересоздаёт сам индекс без копирования строк таблицы. При новом
переименовании PostgreSQL использует `ALTER INDEX … RENAME`.

У уже созданных приложений исходники `manage` и реестров находятся в самом
проекте. При обновлении core перенесите изменения соответствующего шаблона
в свой CLI. В modular подключите также реестр `src/che_sync_migrations/mod.rs`
к списку источников. Существующие файлы миграций и их зависимости сохраняются.
