# Проект архитектуры: история, владение и план миграций

**Статус: каталог и политика генерации реализованы в core.** Публичный интерфейс описан в
[руководстве](migrations.md). Критерий для нового генератора: он либо выдаёт
проверяемый план с понятным эффектом на данные, либо объясняет, какую операцию
должен задать автор. Равенства конечных схем недостаточно: `DROP TABLE` +
`CREATE TABLE` тоже его достигает.

## Границы ответственности

| Часть               | Вход → выход                                                                                               | За что отвечает                                                                  |
| ------------------- | ---------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| Реестр приложения   | Реестры всех крейтов → каталог объектов и неизменяемый граф истории                                        | Владельцы, стабильные идентификаторы, явные внешние требования                   |
| Планировщик в core  | Состояние из истории + каталог желаемой схемы + явные намерения → граф логических операций или диагностика | Переход между состояниями, зависимости и допустимость автоматизации              |
| SQLite / PostgreSQL | Логические операции + границы файлов → физический план                                                     | Возможности backend, ограничения FK, транзакции, перенос строк при перестройке   |
| CLI и исполнитель   | Валидированный план → файлы; затем скомпилированная история → БД                                           | CLI записывает файлы; исполнитель применяет их и фиксирует историю транзакционно |

В `modular` файл остаётся в крейте владельца, в `single` — в общем реестре. Типы
Rust и Cargo-зависимости помогают собрать приложение, но порядок сборки не
задаёт порядок DDL. `--dry-run`, `--check` и запись используют один план; старые
миграции при запуске не пересчитываются из моделей.

## Каталог: кто предоставляет ресурс?

Ресурс — это, например, таблица, колонка, уникальный ключ или FK. Владелец,
логическая идентичность и текущее SQL-имя — три разных свойства. Каталог
индексируется как по идентичности, так и по физическому имени в пространстве
имён backend. Несколько поставщиков одного физического объекта — ошибка.

- **Модель ORM** предоставляет таблицу, колонки и ключи из типизированной схемы.
- **Зарегистрированный SQL-объект** также имеет владельца. Для новой SQL-таблицы
  автор указывает предоставляемые ключи и необходимые ресурсы, если от них
  зависит автоматический план. Например, `parents` предоставляет таблицу
  `raw_parent` и уникальный ключ `id`. SQL остаётся телом операции. Зависимости
  произвольного SQL нельзя надёжно вывести поиском слов в строке.
- **Внешний объект** имеет явное требование к окружению, но не имеет миграции-
  поставщика в проекте. Перед применением требование проверяет backend; сам FK
  по-прежнему устанавливается в БД. Если объект есть в каталоге SQL-объектов, он
  не может одновременно считаться внешним. Неизвестная цель без декларации даёт
  диагностику с именем поля и подсказкой, что зарегистрировать.

Для прежних `references = "table(column)"` сначала искать цель во всём каталоге.
Для действительно неизвестной цели предусмотреть переходный режим с
предупреждением и инструкцией добавить внешнее требование. Новые декларации и
диагностика не должны менять сериализацию или контрольные суммы уже выпущенных
операций.

## Что генератор может делать сам

| Изменение                                                                                 | Решение                                                                                                                    |
| ----------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| Добавление таблицы, nullable-колонки или индекса                                          | Структурная операция с известными предпосылками                                                                            |
| Переименование с сохранением идентичности                                                 | Перенос имени; существующие строки и ссылки сохраняются                                                                    |
| Изменение SQL тела таблицы, неизвестное преобразование типа, неоднозначное переименование | `NeedsManualMigration`: явный `ALTER` или перенос данных и описание итогового состояния                                    |
| Исчезновение таблицы или колонки из реестра                                               | Кандидат на удаление, а не разрешение стереть данные. Предложить конкретный объект; требовать явного намерения удалить его |
| Добавление обязательного поля к существующим данным                                       | Явный default или последовательность «nullable → заполнение → ограничение» с проверкой данных                              |

Для SQL-таблицы `notes` добавление `caption` в текст `CREATE TABLE` не даёт
генератору права удалять `notes`. Даже если таблица сейчас пуста, результат
офлайн-генерации должен быть тем же. Для SQLite допустима физическая перестройка
таблицы, когда редактор умеет явно сопоставить старые и новые колонки, перенести
строки и восстановить ограничения и зарегистрированные объекты. Если это нельзя
гарантировать, нужен ручной переход. Ручной SQL описывает эффект на состояние;
неописанные эффекты нельзя использовать для автоматической перестановки
операций.

## Один граф операций; граф файлов выводится из него

1. Восстановить исходный каталог из зафиксированной истории. Сравнить его с
   желаемым каталогом по идентичностям. Разделить обнаруженное изменение,
   разрешённое намерение и конкретную SQL-реализацию.
2. Для каждой логической операции определить, какие ресурсы она требует,
   предоставляет, переименовывает и освобождает. Строить рёбра как по старой,
   так и по новой схеме: создать или переименовать цель **до** добавления FK;
   снять или перевести FK **до** удаления цели. Самоссылка снимается вместе с
   собственной таблицей. Для независимых операций использовать стабильный
   порядок только для воспроизводимости вывода.
3. Выделить циклы. Два взаимных FK внутри файла можно отложить до конца файла,
   если это поддерживает backend. Для цикла между владельцами сначала оценить
   разбиение на создание таблиц и последующую установку FK. Если существующий
   набор операций не поддерживает разбиение без потери данных, показать цепочку
   `приложение.таблица.поле → целевой ключ` и остановиться до записи.
4. Сгруппировать операции в транзакционные файлы владельцев. Одному крейту
   иногда нужны два файла за запуск, например при порядке `A → B → A`.
   Межфайловые зависимости — только пересекающие границу рёбра плюс предыдущая
   миграция собственного приложения. У каждого ребра сохранять причину для
   диагностики. Независимое приложение не становится обязательным предком.
5. Проверить воспроизведение всего графа **и каждого файла только с его
   предками**. В конце каждой транзакции управляемые FK должны быть разрешены.
   Пробное применение и реальный исполнитель должны использовать одни правила
   backend. Офлайн-проверка не доказывает свойства существующих строк или
   внешней БД; проверки таких предпосылок относятся к применению, до фиксации
   истории.

Например, для `children.parent_id → raw_parent.id` в другом крейте каталог даёт
ровно одно ребро: `parents:0001 → children:0001`. Если `raw_parent`
действительно внешняя таблица, миграции `parents:0001` нет: вместо ребра план
содержит проверку внешнего ключа-кандидата `raw_parent.id`.

## Внедрение и критерии выпуска

1. Зафиксировать контракты тестами на SQLite и живом PostgreSQL. Два блокирующих
   случая: изменение SQL таблицы с существующей строкой (данные сохранены либо
   отказ до записи) и создание межкрейтового FK на зарегистрированную
   SQL-таблицу (чистая база, полное и целевое применение).
2. Ввести каталог и тип результата `Plan | NeedsManualMigration | InvalidSchema`
   внутри core. Проверить импорт старой истории: те же ID, зависимости и
   контрольные суммы. Для непрозрачной истории разрешать явное описание
   состояния новой миграцией; не угадывать его и не редактировать старый файл.
3. Реализовать граф ресурсов и группировку файлов. Сравнить планы на постоянном
   наборе схем до переключения шаблонов. Прогнать также переименование с
   данными, удаление родителя после снятия FK, циклы, внешнюю и ошибочно
   указанную цель, отказ при конфликте владельцев. Перестановка порядка
   регистрации независимых приложений не должна менять результат.
4. Переключить оба шаблона на один контракт совместно с версией core. Запись
   исходников начинается после валидации всех файлов; при ошибке записи
   восстанавливается весь комплект. Сбой применения откатывает текущий файл и
   его запись истории, повторный запуск продолжает с последнего коммита.
   Проверить это на реальных БД, в том числе повторный `migrate` с нулём
   операций.

Оба блокирующих сценария проверяет `catalog_owns_sql_tables_and_rejects_destructive_replacements`
на SQLite и PostgreSQL, включая целевое применение, отказ от разрушительной
замены и сохранность строки после ручного `ALTER TABLE`. Неизвестные внешние
цели допускаются в режиме совместимости; строгий режим включается через
`GenerationPolicy::strict_external`. Автоматическое разбиение циклов между
крейтами на отдельные DDL-фазы остаётся за пределами текущего планировщика.
